## 构建失败根因定位（17:39 用户实测确认）
- 现象：跑 `SpeedScript/compile.bat 2.0.2-alp.1`，日志尾部只有 webpack 的 performance WARNING，紧跟一句「构建失败, 请检查上方错误信息。」，**通篇没有任何 "ERROR" 字样**，用户因此以为"只有 WARNING 却失败"。

  - 含义：**`wsl.exe` 存在（Windows 自带 stub），不是"没装 WSL"**；是 WSL2 依赖的 **VirtualMachinePlatform / Microsoft-Windows-Subsystem-Linux 可选功能未启用**，或 BIOS 虚拟化（VT-x/AMD-V）没开，或本机是虚拟机且未开嵌套虚拟化。

- **`compile.bat` 的四个反调试特性（下次别再被绕进去）**：
  1. `:error`（第 180-185 行）只打一句笼统中文，**不打印失败步骤** —— 日志里根本看不出哪步挂的。

  3. 前两步失败（第 56-60 行 WSL 路径转换 / 第 64-68 行 WSL 用户名探测）打印的是**中文提示、没有 "ERROR"**，在"找 ERROR"时极易被忽略。

## WSL 修复完成（18:06 用户实测确认）——构建失败的最终解
- **最终根因**：`vmcompute` 服务 **Stopped**。`HCS_E_SERVICE_NOT_AVAILABLE` 里的 HCS 就是 Host Compute Service = `vmcompute`，错误码是字面意思。
- **修复**：管理员 PowerShell 跑 `Start-Service vmcompute` → 用户回「成了」，WSL 恢复。
- **已被排除的因素**（全部正常，别再往这些方向查）：`VirtualMachinePlatform` 已启用、`Microsoft-Windows-Subsystem-Linux` 已启用、`hypervisorlaunchtype = Auto`、`systeminfo` 报「已检测到虚拟机监控程序」（= hypervisor 确实在跑）、`HvHost` Running、`WslService` Running/Automatic。
- **重要细节**：`vmcompute` 的 StartType 本是 `Manual`，平时 Stopped **属正常设计**（靠 WSL 启动时的触发器拉起）。手动能起 = **触发器失败或被外部拦截**，不是配置错误。若重启后复发，用 `sc.exe config vmcompute start= auto` 固化为自启。
- **PowerShell 坑（务必记住）**：`bcdedit /enum {current}` 在 PowerShell 里 `{current}` 会被解析成 **scriptblock**，命令静默失效、**无任何输出**（易被误判为"该键不存在"）。必须写 `bcdedit /enum "{current}"`；只有 cmd 里才不需要引号。
- **标准诊断顺序（以后直接照抄）**：
  1. `Get-Service vmcompute,HvHost,WslService | Format-Table Name,Status,StartType -AutoSize`
  2. `bcdedit /enum "{current}" | Select-String hypervisorlaunchtype`
  3. `systeminfo | Select-String "Hyper-V"`
- **另注**：`wsl --update` 报 `0x80190193` = HTTP 403，属**网络层**（代理/CDN 拦截）问题，与 `HCS_E_SERVICE_NOT_AVAILABLE` **无因果**；且 `wsl --update` 修不了 HCS 问题，别把顺序搞反。

## 构建失败第 2 根因（18:13 定位并修复）—— webpack 4 × markdown-it ESM
- 现象：WSL 修好后重跑 `compile.bat` 仍「构建失败」，日志尾部只有 performance WARNING。定位手法：单独跑
  `env -u NODE_OPTIONS -u ELECTRON_RUN_AS_NODE npm run webpack:prod > webpack-log.txt 2>&1` → **EXIT=1**，抓到真错误。
- **真因**：`markdown-it@14` 是**纯 ESM（`.mjs`）**包；webpack **4.47.0** 把 `.mjs` 当严格 ESM 解析、**禁止 CommonJS 互操作**，编译报 12 条
  `ERROR in ./node_modules/markdown-it/lib/*.mjs — Can't import the named export 'X' from non EcmaScript module (only default export is available)`
  → **gui entry 整体编译失败**。addons entry 小、先编完，所以用户只看到 addons 那半边的 WARNING（`index.js 873 KiB` 正是 addons 产物大小）。
- **修复**：`webpack.config.cjs` 的 `module.rules` 末尾加一条
  `{ test: /\.mjs$/, type: 'javascript/auto' }`（带注释说明原因）→ 重跑 webpack **EXIT=0**。
- **产物变化**：`dist-renderer-webpack/editor/gui/index.js` 7.70MB(17:01 旧) → **7.84MB(18:13 新)**，增量 ~140KB = markdown-it + dompurify。
- **通用教训**：webpack 4（2018）对 `.mjs` 的处理与当今 ESM-only npm 包不兼容。以后引入任何 ESM-only 依赖（`.mjs`，或 `"type":"module"` 且 `exports` 无 CJS 入口）都需先加这条 rule。
- **遗留 WARNING（无害，非 ERROR，可忽略）**：`Conflict: Multiple assets emit different content to the same filename index.js`、两条 244KiB performance warning。
- **诊断产物**：`webpack-log.txt`（仓库根目录）是本次复现留下的，可删。
- **命令行坑**：`cd /d "路径"` 是 **cmd** 语法，PowerShell 里会报 `Set-Location: 找不到接受自变量 '...' 的位置参数`。PowerShell 直接 `cd "路径"`。
